# 💡 시맨틱 태그(Semantic Tag)를 사용하는 이유 심화
> 코드를 직관적으로 파악하고(가독성) 유지보수를 쉽게 하는 기본 목적 외에, 브라우저와 시스템에 코드의 '의미'를 전달하는 두 가지 핵심 역할이 있습니다.

## 1. 웹 접근성 (Web Accessibility) 향상
* 시각 장애인이 사용하는 스크린 리더 등 보조 기기가 웹 페이지를 읽을 때 시맨틱 태그가 아주 중요한 이정표가 됩니다.
* 현재 읽고 있는 영역이 내비게이션인지, 핵심 본문인지 명확히 구분하여 사용자에게 음성으로 정확하게 안내할 수 있습니다.

## 2. 검색 엔진 최적화 (SEO)
* 구글 같은 검색 엔진 봇이 페이지를 수집할 때, 어떤 부분이 중요 콘텐츠이고 어떤 부분이 부가 정보인지 쉽게 파악할 수 있게 해줍니다.
* 모두 똑같은 `<div>`로 구성된 문서보다 `<main>`, `<article>` 등으로 구조화된 문서가 검색 결과 노출에 훨씬 유리해집니다.

## 프로젝트 소개

코디세이 올인원 과정을 수강하며, HTML/CSS/JavaScript의 기초 문법을 실제로 눈에 보이는 결과물로 익히기 위해 만든 개인 포트폴리오 사이트입니다. 별도의 프레임워크나 빌드 도구 없이, 순수 HTML/CSS/JavaScript(바닐라 JS)만으로 아래 기능들을 직접 구현하는 것을 목표로 했습니다.

- CSS 변수(Custom Properties)를 이용한 다크모드 테마 전환
- GitHub REST API를 활용한 비동기 데이터 연동
- 모바일 퍼스트 반응형 레이아웃

## 주요 기능

### 1. Hero — 타이핑 애니메이션
- 첫 화면에 들어서면 인사말이 타자기처럼 한 글자씩 나타나고, 문장이 끝나면 잠시 대기했다가 다시 처음부터 반복되는 애니메이션을 순수 JavaScript(`setTimeout` 재귀 호출)로 구현했습니다.
- CTA 버튼(`친구 되기!`) 클릭 시, 페이지 새로고침 없이 Contact 섹션으로 부드럽게 스크롤 이동합니다(`scrollIntoView`).

### 2. About
- 프로필 이미지와 소개 문구를 배치했습니다. 모바일에서는 세로로, 태블릿 이상에서는 가로로 배치되도록 반응형으로 구성했습니다.

### 3. Skill
- 사용 가능한 기술 스택을 태그(pill) 형태로 나열했습니다.

### 4. Projects — GitHub API 연동
- GitHub REST API(`/users/{username}/repos`)를 `fetch`로 호출해, 본인이 소유한(owner) 저장소 목록을 가져와 카드 형태로 동적 렌더링합니다.
- **로딩 / 에러 / 빈 상태**를 모두 화면에 텍스트로 표현합니다.
  - 로딩 중: "불러오는 중..." 문구 표시
  - API 요청 실패(네트워크 오류, 잘못된 아이디 등): 에러 안내 문구 표시
  - 저장소가 0개인 경우: "해당하는 프로젝트가 없어요" 문구 표시
- **언어별 필터링**: 각 저장소의 `language` 값을 기준으로 필터 버튼을 자동 생성하고, `Array.prototype.filter()`를 사용해 선택한 언어에 해당하는 프로젝트만 다시 렌더링합니다. "전체" 버튼으로 필터를 해제할 수 있습니다.

### 5. Contact — 문의 폼
- `label`의 `for`와 입력 요소의 `id`를 매칭시켜 접근성을 확보했습니다.
- `required` 속성으로 필수 입력 항목의 기본 유효성 검사를 처리했습니다.
- `event.preventDefault()`로 폼의 기본 제출 동작(페이지 새로고침)을 막고, 자바스크립트로 자체 제작한 안내 메시지를 화면에 표시하도록 구현했습니다(브라우저 기본 `alert()` 팝업 대신 사용).

### 6. 다크모드
- CSS 변수(`:root`)에 색상 값을 정의해두고, `[data-theme="dark"]` 선택자로 다크모드용 값을 덮어쓰는 방식으로 구현했습니다.
- `prefers-color-scheme` 미디어 쿼리로 사용자의 운영체제 다크모드 설정을 감지해, 사용자가 직접 선택하기 전까지는 시스템 설정을 따르도록 했습니다.
- `localStorage`를 이용해 사용자가 선택한 테마를 저장하고, 새로고침 후에도(브라우저를 완전히 껐다 켜도) 마지막 선택이 유지되도록 했습니다. 우선순위는 **사용자의 직접 선택 > 시스템 설정 > 기본값(라이트)** 순입니다.

### 7. 반응형 내비게이션
- 모바일 퍼스트 방식으로 작성했습니다. 기본(가장 좁은 화면) 스타일을 먼저 정의하고, `min-width` 미디어 쿼리로 화면이 넓어질 때 스타일을 추가하는 방식입니다.
- 브레이크포인트: `768px`(태블릿), `1024px`(데스크톱)
- 768px 미만에서는 메뉴가 숨겨지고 햄버거 버튼이 나타나며, 버튼 클릭 시 메뉴가 열리고 닫힙니다.
- 스크롤이 60px 이상 내려가면 헤더 배경색과 글자색이 바뀌도록 처리했습니다(`window.scrollY` 값을 감지해 클래스를 추가/제거하고, 실제 스타일은 CSS에서 정의).

## 배운 개념 정리

프로젝트를 진행하며 새롭게 알게 된 개념들을 정리했습니다. 서로 연결되는 개념끼리는 묶어서 정리했습니다.

### 개발 환경 — VS Code Live Server
VS Code의 Live Server 확장 프로그램을 사용하면, 코드를 수정하고 저장하는 즉시 브라우저 화면에 변경 사항이 자동으로 반영된다. 매번 파일을 새로고침할 필요가 없어 개발 과정에서 매우 편리했다.

### 문서 구조의 기본 — DOCTYPE, head, body
`<!DOCTYPE html>` 선언문은 브라우저에게 "이 문서는 최신 HTML5 표준 규격으로 작성되었으니 최신 엔진으로 해석하라"고 알려주는 지시어다. 이 선언이 없으면 브라우저가 옛날 방식의 호환 모드(Quirks Mode)로 화면을 그려 레이아웃이 깨질 수 있다. 다른 사람과의 버전 차이나 코드 충돌을 막아주는 기능이 아니라, 브라우저가 문서를 해석하는 방식 자체를 지정하는 스위치라고 이해하면 된다.

문서 구조는 무대에 비유할 수 있다. `<head>`는 웹사이트가 정상적으로 작동하기 위해 필요한 설정과 연결 정보를 담당하는, 말하자면 "무대 뒤의 준비 작업"이고, `<body>`는 사용자에게 실제로 보여지는 모든 콘텐츠, 즉 "관객이 보는 무대 위"에 해당한다.

### 태그별 역할 구분 — `<a>`, `<link>`, `<script>`
세 태그는 이름이 비슷해 보여도 역할이 완전히 다르다.

- **`<a>`(Anchor) 태그**는 사용자가 클릭해서 다른 페이지나 문서 내 특정 위치로 이동하는 하이퍼링크를 만들 때 사용한다. `<a>` 태그로 다른 페이지를 이동하면 브라우저는 그 페이지의 HTML 문서를 처음부터 다시 통째로 다운로드한다.
- **`<link>` 태그**는 클릭해서 이동하는 링크가 아니라, 브라우저가 문서를 읽을 때 CSS 스타일시트나 파비콘 같은 외부 리소스를 연결해 주는 통로 역할을 한다. `<a>`와 달리 페이지 전체를 새로 요청하는 게 아니라 필요한 리소스 파일만 요청하기 때문에 리소스를 덜 사용한다. 대표적인 활용 예로, 브라우저 탭 옆에 표시되는 작은 아이콘(파비콘)을 연결할 때도 `<link rel="icon">`을 사용한다. `link`의 `rel` 속성은 연결하려는 파일이 문서와 어떤 관계인지 브라우저에게 알려주는 값인데, `stylesheet`, `icon`처럼 정해진 표준 규격 이름을 사용해야 브라우저가 올바르게 인식한다.
- **`<script>` 태그**는 자바스크립트 파일을 연결하거나, 태그 안에 직접 자바스크립트 코드를 작성할 때 사용한다.

즉, 파일의 종류(문서 이동 / 외부 리소스 연결 / 스크립트 실행)에 따라 사용하는 태그가 다르다.

### 시맨틱 태그를 쓰는 이유, 그리고 `<section>` vs `<article>` vs `<div>`
시맨틱 태그를 사용하면 단순한 화면 분할(`<div>`)을 넘어 브라우저와 보조 기기에 코드의 "의미"를 전달할 수 있다. 이는 크게 두 가지 효과를 가져온다. 첫째, 스크린 리더 같은 보조 기기가 웹페이지의 구조(내비게이션, 본문 등)를 정확히 읽어 음성으로 안내할 수 있게 되어 웹 접근성이 향상된다. 둘째, 검색 엔진 봇이 중요 콘텐츠와 부가 정보를 쉽게 파악할 수 있어 검색 결과 노출(SEO)에 유리해진다.

`<article>`, `<section>`, `<div>`는 겉으로 보기엔 비슷해 보이지만 판단 기준이 명확하다. 만약 그 자리에 `<div>`를 써도 아무런 의미 손실이 없다면 원래 `<div>`를 쓰는 게 맞고, 태그를 통해 의미를 부여할 수 있는 자리라면 시맨틱 태그를 쓰는 것이 맞다. `<section>`과 `<article>`의 차이는 다음과 같다.

- **`section`**: 문서 안에서만 의미가 통하는 "주제 구획"이다. 문서에서 떼어내면 문맥이 사라진다. (예: 최근 게시글, 학력)
- **`article`**: 혼자 떼어내도 내용이 완결되는 "독립 콘텐츠"다. (예: 블로그 글 하나, 뉴스 기사 하나)
- 구조적으로는 `section`(챕터) 안에 여러 개의 `article`(개별 항목)이 들어가는 경우가 많다.
- 판단법: "이것만 떼어서 다른 곳에 놔도 말이 되는가?" → 말이 되면 `article`, 안 되면 `section`.

### HTML 엔티티
HTML에서 `<`, `>`, `&`, `"` 같은 기호는 태그 문법에 사용되는 예약 문자이기 때문에, 화면에 그 기호 자체를 그대로 표시하고 싶을 때는 정해진 대체 표기(엔티티)를 사용해야 오류 없이 출력된다.

| 기호 | 엔티티 |
|---|---|
| `<` | `&lt;` |
| `>` | `&gt;` |
| `&` | `&amp;` |
| `"` | `&quot;` |

### `class` vs `id`
| 구분 | class | id |
|---|---|---|
| 중복 가능? | O (여러 요소에 반복 사용) | X (문서당 1개만) |
| CSS 선택자 | `.skill` | `#skill` |
| 주 용도 | 같은 스타일 그룹 적용 | 고유한 하나의 요소 지칭 |
| 예시 | 상품 카드들, 버튼들, 스킬 항목들 | 헤더, 특정 앵커 위치(`href="#about"`) |

### CSS 선택자 심화 — `:`와 `::`, `:root`
`:`은 `:hover`처럼 요소의 특정 상태를 선택하는 가상 클래스(pseudo-class)에 사용하고, `::`는 `::before`, `::after`처럼 실제 HTML에는 존재하지 않지만 CSS로 새로 생성하는 가상 요소(pseudo-element)에 사용한다. `:root`는 문서의 최상위 요소를 가리키며, 프로젝트 전체에서 재사용할 전역 CSS 변수(Custom Properties)를 선언할 때 주로 사용한다.

### 이미지 스타일링
프로필 이미지를 원형으로 다듬을 때 사용한 속성들이다.

- `width`, `height`: 이미지가 차지할 영역의 크기를 지정한다.
- `object-fit: cover`: 이미지의 원본 비율을 유지하면서 지정된 영역을 꽉 채우도록 한다(비율이 다른 이미지가 찌그러지지 않게 함).
- `border-radius: 50%`: 네모난 이미지를 원형으로 보이게 만든다.
- `flex-shrink: 0`: flex 레이아웃에서 화면이 좁아져도 해당 요소(이미지)의 크기가 줄어들지 않도록 고정한다.
- `background-color`: 요소의 안쪽 배경색을 채운다(이미지 로드 전이나 투명 영역에 대한 배경).

또한 `<img>` 태그의 `alt` 속성은 마우스를 올렸을 때 설명을 보여주는 용도가 아니라, 이미지가 로드되지 않았을 때 대체 텍스트를 보여주거나 스크린 리더가 읽을 수 있도록 하는 접근성 목적의 속성이다. 마우스를 올렸을 때 말풍선처럼 설명이 뜨게 하려면 `title` 속성을 별도로 사용해야 한다.

### 비동기 처리 — `fetch`, `Promise`, `async`/`await`
GitHub API에서 데이터를 가져올 때 사용한 세 개념은 역할이 서로 다르다.

| 항목 | fetch | Promise | async/await |
|---|---|---|---|
| 정체 | HTTP 요청 API | 비동기 결과를 담는 객체 | Promise를 다루는 문법 |
| 역할 | 요청을 보냄 | 비동기 작업의 결과(성공/실패)를 담음 | 결과를 동기 코드처럼 읽기 쉽게 처리 |
| 단독 사용 | 요청용으로 사용 가능 | 가능 | 불가능(반드시 Promise 기반 위에서 동작) |
| 가독성 | 보통 | `.then()` 체인이 길어지면 낮아짐 | 상대적으로 높음 |
| 에러 처리 | 그 자체로는 에러 처리 기능 없음 | `.catch()` | `try`/`catch` |
| 실무 사용 빈도 | 매우 많음 | 매우 많음 | 매우 많음 |
| 대표 조합 | `fetch` + `.then()` | Promise 체이닝 | `fetch` + `async`/`await` |

### 인터랙션을 위한 CSS 속성
| 개념 | 의미 |
|---|---|
| `:hover` | 마우스를 올렸을 때 적용되는 CSS |
| `transition` | 스타일 변화가 순간적으로 바뀌지 않고 부드럽게 일어나게 함 |
| `box-shadow` | 요소에 그림자를 추가함 |
| `transform` | 이동, 확대, 회전 같은 시각적 변형을 적용함 |

프로젝트 카드에 마우스를 올렸을 때(hover), 스크롤 시 화면 이동 등 부드러운 느낌을 주는 `transition` 속성은 대부분 `0.3s`로 통일해서 설정했다. 값을 통일하면 사이트 전반의 인터랙션 속도감이 일관되게 느껴진다.

### 로컬스토리지(localStorage)
로컬스토리지는 브라우저가 제공하는 데이터 저장 공간으로, 페이지를 새로고침하거나 브라우저를 완전히 껐다 켜도 데이터가 사라지지 않고 계속 남아있는 것이 특징이다. 이 저장소는 웹사이트(도메인) 단위로 구분되어 있어서, 한 사이트에서 저장한 데이터는 다른 사이트에서는 보이지 않고 오직 그 사이트에서만 다시 꺼내볼 수 있다.

기존에 사용하던 `data-theme` 같은 HTML 속성은 지금 열려있는 페이지가 살아있는 동안에만 유지되는 값이라서, 새로고침을 하면 브라우저가 HTML 파일을 처음부터 다시 읽어오면서 그 값이 사라진다. 반면 로컬스토리지에 저장한 값은 이런 새로고침과 무관하게 계속 남아있기 때문에, 다크모드 설정처럼 "사용자가 선택한 상태를 기억해야 하는" 기능을 만들 때 적합하다.

사용법은 크게 세 가지다. `localStorage.setItem(키, 값)`으로 원하는 이름표를 붙여 값을 저장하고, `localStorage.getItem(키)`로 그 이름표에 해당하는 값을 다시 꺼내오며, `localStorage.removeItem(키)`로 저장된 값을 지울 수 있다. 단, 로컬스토리지는 문자열(string)만 저장할 수 있어서, 숫자나 다른 타입의 값을 넣어도 내부적으로 자동으로 문자열로 변환되어 저장된다.

비슷한 이름을 가진 `sessionStorage`도 있는데, 이는 브라우저 탭을 닫으면 데이터가 사라지는 임시 저장소라는 점에서 로컬스토리지와 다르다. "새로고침해도 유지"되는 정도가 아니라 "브라우저를 완전히 껐다 켜도 유지"되길 원한다면 로컬스토리지를 사용해야 한다.

다크모드 기능에 적용한 흐름은 다음과 같다. 먼저 사용자가 다크모드 버튼을 누르면 로컬스토리지에 현재 테마 값을 저장한다. 이후 페이지가 다시 열릴 때마다, 로컬스토리지에 저장된 테마 값이 있는지 확인하고, 있다면 그 값을 읽어와 페이지가 그려지기 전에 미리 해당 테마를 적용한다. 이렇게 하면 새로고침을 하거나 브라우저를 다시 열어도 마지막으로 선택했던 다크모드 상태가 그대로 유지된다.

## 트러블슈팅 기록

- **CSS/JS 파일이 적용되지 않던 문제**: `<link>`, `<script>`의 경로(`href`, `src`)가 실제 파일 위치와 일치하지 않아 발생한 문제였다. 브라우저 개발자 도구의 Network 탭에서 404 응답을 확인하고, 실제 폴더 구조에 맞게 상대 경로를 수정해 해결했다.
- **GitHub API에서 팀 프로젝트/비공개 저장소가 보이지 않던 문제**: GitHub의 공개 API는 인증 없이는 비공개(private) 저장소를 반환하지 않는다는 점을 확인했다. 토큰을 클라이언트 코드에 직접 넣는 방식은 보안상 위험하므로, 소유자(`owner.login`) 기준으로 필터링해 공개된 개인 저장소만 노출하는 방향으로 정리했다.
- **flex 정렬이 미묘하게 어긋나던 문제**: `<a>`와 `<button>`처럼 브라우저 기본 스타일이 서로 다른 요소를 같은 줄에 배치할 때, `line-height`와 기본 높이 차이로 정렬이 어긋났다. 각 `<li>`와 내부 요소에 명시적인 `height`와 `align-items: center`, `line-height: 1`을 지정해 해결했다.
